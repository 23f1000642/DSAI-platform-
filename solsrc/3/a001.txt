=== 3.0.1
The three-schema architecture has three levels:

- **Internal (physical)**: how the data is stored.
- **Conceptual**: the whole logical database.
- **External**: the individual *views* given to each user.

Hiding the salary column from employees means giving them an external view without that column. This is **external-level data hiding**, **option C**.

=== 3.0.3
Concurrent updates to the same record are serialised by **locking**. While one transaction holds an exclusive (write) lock on the record, the other must wait. **Option D**.
=== 3.0.4
Suppose T1 updates an item and then fails (rolls back), but T2 has already read the uncommitted value. T2 is now working with "dirty" data. This is the **dirty read problem**, also called the temporary update problem. **Option C**.
=== 3.0.5
In the CODASYL/network model, the **User Work Area (UWA)** is a set of program variables declared in the host program. Records move between the **host program and the DBMS** through it: GET loads a record into the UWA, and STORE writes it from the UWA. **Option C**.
=== 3.0.6

=== 3.0.14

=== 3.0.15
- **D1 is false.** Decomposing $R(A,B,C)$ into $(A,B)$ and $(A,C)$ is lossless only if $A\to B$ or $A\to C$. That isn't true in general.
- **D2 is true.** $R_1\cap R_2 = \{A,D\}$, and $AD\to B$ is given. So $AD$ determines all of $R_1 = \{A,B,D\}$, i.e. the common attributes are a superkey of $R_1$. The decomposition is lossless.

**Only D2**, **option D**.
=== 3.0.16
- **Privacy invasion** (A), **hardware failure** (B) and **fraudulent manipulation of data** (C) are all genuine threats to data security.
- **Encryption and decryption** (D) is a *protection* mechanism, not a threat.

The original paper's single intended option isn't recoverable, and the official key was never published. Treat A, B and C as threats, and D as the odd one out.

=== 3.0.19
$a$ in $R_1$ is a foreign key referencing $R_2$'s primary key.

- **(a) Insert into $R_1$** can violate referential integrity: the new $a$ value may not exist in $R_2$.
- **(b) Insert into $R_2$** is always safe.
- **(c) Delete from $R_1$** is always safe.
- **(d) Delete from $R_2$** can violate it: a row of $R_1$ may still refer to the deleted key.

**(a) and (d)**, **option D**.
