- **I is true.** Conservative 2PL locks everything a transaction needs **before** it starts, so it never waits while holding locks. No deadlock.
- **II is false.** Thomas's write rule ignores obsolete writes. It gives **view** serialisability, not conflict serialisability.
- **III is true.** Timestamp ordering serialises transactions in timestamp order.

=== 3.57.1
**Serialisability:**

- T1's Read A comes before T2's Write A, giving T1→T2.
- T2's Write B comes before T1's Read/Write B, giving T2→T1.

That's a cycle, so the schedule is **not serialisable**.

**2PL:** 2PL produces only conflict-serialisable schedules, so this schedule **can't occur** under 2PL.

Suppose a transaction reads data written by an **uncommitted** transaction and then commits. If the writer later aborts, the committed reader can't be undone. That's an irrecoverable error. **Option D**.

=== 3.57.7
- **2PL** guarantees conflict serialisability but **can deadlock**.
- **Timestamp ordering** guarantees conflict serialisability and is **deadlock-free**, because transactions never wait.

**II only**, **option B**.
=== 3.57.8
The conflicts:

- T1 Read(X) and Write(X) come before T2 Read(X) and Write(X): **T1→T2**
- T1 Write(X) comes before T3 Write(X): **T1→T3**
- T3 Read(Y) comes before T2 Write(Y): **T3→T2**
- T3 Write(X) comes before T2 Read(X) and Write(X): **T3→T2**

The graph is acyclic, so the serial order is **T1 → T3 → T2**. **Option A**.
